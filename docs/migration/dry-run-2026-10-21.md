# Opening-balance dry run, 2026-10-21 (fictional data)

Prepared by the migration-agent. **Every amount, name and number here is fictional**: the dry-run fixture
`migration/fixtures/dry_run.py`. No Almiras or Falcon data was read, and no real export is committed. This report
shows that the migration path works. It is not the tie-out of a real load, so the accountant does not sign it off.

Run: `migration/test_dry_run.py` (6 tests) on SQLite, through the same commands and services the runbook (spec §10)
uses. The files are written to a scratch folder, not to git. The fixture data is shaped like a Falcon migration:

## What the dry run proved

1. **Workbook (W4 to W11).** Both TBs balance to the halala. Every code with a balance is mapped to a postable ERP
   account of the right class. Every sub-ledger tie-out above is zero. The only warning is `bai_ajel_contracts`
   (see gap 4).
2. **Falcon journal to TB (R11).** For each of the 20 codes, the TB opening plus the journal's December movement equals
   the TB closing (journal total 209,932.11). The CSV TB closing equals the workbook TB code by code.
3. **Mapping (R12, R13).** The map drafted from the workbook equals the CSV map. The preparer cannot approve it; a
   second person approves it.
4. **Loading (R14).** A dry run writes nothing. The applied run drafts one entry per entity. Each draft is balanced,
   every line has one side only with 2 decimals, and every account belongs to the entity. The 1210 line carries the
   counterparty DRYS. A re-run skips the entry and creates no duplicate.
5. **Control accounts (B2, M6, M7, R8, R22).** The opening entry may carry 1200, 1210, 2100 and 2110 balances. It
   posts only after the R22 gate passes:
   - A load 0.01 short on 1200 is refused (en/ar, with account and amount), and nothing posts.
   - The exact load posts.
   - When no open-item source is registered, posting is refused.
   - Replaying the Falcon journal is refused, because 4 of its entries touch 1201 or 2101.
6. **Posting (R16).** The preparer cannot post. The approver posts both entries, and each goes through
   `ledger.services.post_entry`, which a spy confirmed.
7. **Restricted accounts.** 1140 (purification) and the bai' ajel accounts 1240, 1241 and 4610 accept the opening
   entry, which uses the migration allowance. After posting, a manual journal on any of the four is refused
   (`restricted_account`).
8. **Sharia per entity (rule 5, OQ-10).** DRYS does not enforce Sharia, and its 2410 loan and 5610 interest load. The
   same 2410 balance in DRYH is an error in the workbook check and in the loader, and nothing is created.
9. **Entity separation (rule 4, R19, R24).** A DRYS-only accountant cannot map or load DRYH, and cannot run the
   workbook check over both entities. A DRYH map row cannot point to a DRYS account. The intercompany lines mirror
   each other: DRYH 1210 (DRYS) + DRYS 2110 (DRYH) = 0.
10. **Rounding.** A SAR amount with 3 decimals is refused, in the workbook and in the TB CSV. It is never rounded. A
    USD open item with 3 decimals is refused (`currency_decimals`).

## Code changes made for this dry run (spec amended 2026-10-21)

- **R8 as amended (AT-23).** On the opening entry, control accounts are listed as an info, not a warning. In a
  replayed journal, each entry that touches a control account is an error naming the entry and the account, and the
  run is refused.
- **R16 as amended.** A replayed import draft with a control-account line is refused at posting.
- **R22 (AT-24).** The posting gate `_open_item_tie_out` compares the entry with the open items reported by sources
  registered through `register_open_items_source`. Until a source is registered, an entry with control-account
  balances is refused.
- **W14 (new).** A 1240 or 1241 balance gives a warning, because no contract detail is held. A 1241 debit balance, or
  a 1241 credit larger than 1240, is an error.
- **Existing tests.** The shared fixture journal no longer replays lines on 1201. The tests that post an opening
  entry now load matching open items.

## Gaps for the real Falcon load (need a builder or a human decision)

1. **R23 open-item loader not built (OQ-12). This blocks every real load.** Open AR/AP are not loaded into invoicing,
   and no source is registered. So by design, the real opening entry of any entity with balances on 1200, 1210, 2100
   or 2110 stays a draft. In this dry run a test source stood in for the loader.
2. **Approval engine (R13, R16, AT-25) not enforced.** A direct `approve_account_map` call is still accepted. Posting
   uses the `ledger.post_entry` grant directly, not a `ledger.manual_entry` engine request.
3. **Falcon TB and chart export formats (OQ-1).** The TB CSV column map is a guess. The real export has to be profiled
   under `exports/` by an authorised person; an agent never sees it.
4. **Bai' ajel contracts (CFO decision).** 1240, 1241 and 4610 load as balances only. The workbook has no contract
   sheet, so 1240 and 1241 are not tied to contracts. No `DeferredSale` contracts are created, so payroll has nothing
   to collect the legacy instalments against.
5. **Other module loaders (OQ-12).** Bank accounts (banking), employees with their end-of-service and leave openings
   (hr / payroll) and the asset register (fixed assets) are only tied out in the workbook. None of them are loaded.
6. **Foreign currency (OQ-13).** The USD bank balance and the USD open item enter the ledger in SAR only. Their
   transaction amounts stay in the workbook, so revaluation cannot use them yet.
7. **Control-account lists differ.** Migration gates 1200, 1210, 2100, 2110, 2310 and 2320; 2310 and 2320 are not in
   the chart. Invoicing also treats VAT (2200, 1310), WHT (2220) and 1140 as control accounts. Someone has to decide
   how opening VAT and WHT balances are evidenced: against the last returns, or not at all.
8. **Purification.** Nothing checks that the 1140 opening balance equals the 2600 charity payable, or any
   purification register. Human decision.
9. **Two cross-checks not built.**
   - The workbook check does not compare intercompany mirrors across entities: DRYH 1210 (DRYS) against DRYS
     2110 (DRYH). Only the test above does.
   - The workbook's Sharia flag is not compared with `Entity.sharia_enforced`. The workbook check uses the sheet's
     flag, and the loader uses the ERP's.
10. **Year replay (OQ-4, OQ-5, OQ-14).** Under M7, a Falcon journal that touches control accounts cannot be replayed.
    Closing TB plus open items is the only workable path. How `مستخلص عميل` movements after the cut-over are handled
    is still open.
11. **Sharia-prohibited legacy balances in a Sharia entity (OQ-10)** block the load. The Sharia board or the CFO
    decides how they are treated.
12. **PostgreSQL.** The run was on SQLite only. The PostgreSQL guards (e.g. `invoicing/0023` restricted accounts) were
    not exercised.

Nothing is posted to a real environment without the accountant's sign-off on the real tie-out report (spec §10,
step 4).
